## Key Question 1: Blockchain structure (blocks, hashes, the previous-block link, Merkle roots, node counts)

### Takeaway
A block is a batch of transactions plus a small header; the header contains the hash of the previous block's header and a Merkle root summarising the block's transactions, so changing any old transaction changes every later link and the altered copy is rejected by other nodes. As of 4 October 2026 there were about 25,200 reachable Bitcoin nodes and about 12,100 discoverable Ethereum nodes, but the Bitcoin figure comes from a tracker that changed operator in 2026.

### Cited Findings

#### (a) Well-established facts, safe to teach

- A Bitcoin block header is 80 bytes and has exactly six fields: version (4 bytes), previous block header hash (32), merkle root hash (32), time (4), nBits, the encoded difficulty target (4), and nonce (4). — [Bitcoin developer reference: block chain](https://developer.bitcoin.org/reference/block_chain.html)
- Bitcoin hashes with SHA256 applied twice, written SHA256(SHA256()). — [Bitcoin developer reference: block chain](https://developer.bitcoin.org/reference/block_chain.html)
- "Each block also stores the hash of the previous block's header, chaining the blocks together. This ensures a transaction cannot be modified without modifying the block that records it and all following blocks." — [Bitcoin developer guide: block chain](https://developer.bitcoin.org/devguide/block_chain.html)
- "Every block must include one or more transactions. The first one of these transactions must be a coinbase transaction." The coinbase output cannot be spent for at least 100 blocks. — [Bitcoin developer guide: block chain](https://developer.bitcoin.org/devguide/block_chain.html)
- Merkle root: "Copies of each transaction are hashed, and the hashes are then paired, hashed, paired again, and hashed again until a single hash remains, the merkle root of a merkle tree." — [Bitcoin developer guide: block chain](https://developer.bitcoin.org/devguide/block_chain.html)
- With an odd number of transaction IDs, "the last TXID is concatenated with a copy of itself and hashed." — [Bitcoin developer reference: block chain](https://developer.bitcoin.org/reference/block_chain.html)
- What a cryptographic hash function guarantees (NIST): the output length is fixed; it is "computationally infeasible to find any input that maps to any pre-specified output" (one-way, preimage resistance); "computationally infeasible to find any two distinct inputs that map to the same output" (collision resistance); and, given one input, "computationally infeasible to find a second (distinct) input value that maps to the same output" (second preimage resistance). The wording is "computationally infeasible", not "impossible". — [NIST CSRC glossary: cryptographic hash function](https://csrc.nist.gov/glossary/term/cryptographic_hash_function)
- The Bitcoin whitepaper describes the structure as: "Each timestamp includes the previous timestamp in its hash, forming a chain, with each additional timestamp reinforcing the ones before it", and "forming a record that cannot be changed without redoing the proof-of-work." — [Bitcoin whitepaper (Nakamoto Institute copy)](https://nakamotoinstitute.org/library/bitcoin/)
- Cost of rewriting history: modifying an old block "requires (on average) as much hashing power to propagate a modified block as the entire Bitcoin network expended between the time the original block was created and the present time." — [Bitcoin developer guide: block chain](https://developer.bitcoin.org/devguide/block_chain.html)
- Nodes independently check blocks: "Nodes accept the block only if all transactions in it are valid and not already spent." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- Light clients need only headers: "A user only needs to keep a copy of the block headers of the longest proof-of-work chain." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- Ethereum: "Blocks are batches of transactions with a hash of the previous block in the chain." A block has `slot`, `proposer_index`, `parent_root` (the hash of the preceding block), `state_root` and a `body`; the execution payload inside the body has `parent_hash`, `fee_recipient`, `state_root`, `receipts_root`, `gas_limit`, `gas_used`, `base_fee_per_gas`, `transactions` and `withdrawals`. — [ethereum.org: blocks](https://ethereum.org/en/developers/docs/blocks/)
- Ethereum time "is divided up into twelve second units called 'slots'"; a slot can be empty if the chosen validator is offline. — [ethereum.org: blocks](https://ethereum.org/en/developers/docs/blocks/)
- Bitcoin block capacity is defined by weight: "Block weight is defined as Base size * 3 + Total size" and "The new rule is block weight ≤ 4,000,000." Virtual size (vbytes) is weight divided by four. BIP status: Deployed. — [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki)

#### (c) Contested or commonly misstated

- "The longest chain wins." Accurate version: nodes "always follow the most difficult chain to recreate", meaning the chain with the most cumulative proof of work. The whitepaper itself says "longest chain, which has the greatest proof-of-work effort invested in it", which is where the loose phrasing comes from. — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html) and [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- "Bitcoin blocks are 1 MB." The Bitcoin developer reference still says "a block is not valid unless its serialized size is less than or equal to 1 MB", but that text predates SegWit; the consensus rule since BIP-141 is block weight ≤ 4,000,000. Do not quote the 1 MB sentence as current. — [Bitcoin developer reference](https://developer.bitcoin.org/reference/block_chain.html), superseded by [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki)
- "A block is added every 10 minutes." Accurate version: new blocks are added "approximately every 10 minutes on average, but block discovery is probabilistic"; "sometimes it can take Bitcoin miners 30 or even 60 minutes to mine a single block." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know) and [Kraken support, updated 1 October 2026](https://support.kraken.com/articles/203325283-cryptocurrency-deposit-processing-times)
- "Blocks contain the previous block." Accurate version: the header contains only the 32-byte hash of the previous block's header. — [Bitcoin developer reference](https://developer.bitcoin.org/reference/block_chain.html)
- "Altering a block is impossible." Accurate version: it is computationally infeasible to do so and have the rest of the network accept it, because the attacker must redo the proof of work for that block and every later block and out-pace the honest network. See Key Question 2 for the cases where history has in fact been rewritten. — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)

#### Step-by-step for animators: what happens when old data is altered (Bitcoin)

1. Someone changes one transaction in an old block on their own copy. That transaction's hash (TXID) changes. — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)
2. Because TXIDs are paired and hashed up the tree, the Merkle root changes. — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)
3. The Merkle root is one of the six header fields, so the header's hash changes, and the new hash almost certainly no longer meets the proof-of-work target ("you must create a hash of the block header which does not exceed a certain value"). — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)
4. The next block's header stores the old hash in its "previous block header hash" field, so the link no longer matches; that block and "all following blocks" would have to be rebuilt. — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)
5. Other nodes keep their own copies, validate independently, and follow the chain that is most difficult to recreate, so the altered copy is simply ignored unless the attacker out-works the rest of the network. — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/) and [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)

### Inferences
- A hash is best depicted as a fixed-length fingerprint, not as encryption: NIST defines it as one-way with no way back to the input, so any animation showing a hash being "decrypted" or "unlocked" would be wrong.
- Metaphor flag, "chain of padlocked boxes": acceptable only if the link is shown as each block carrying the fingerprint of the previous header. It misleads if it implies a physical lock stops tampering. The accurate picture is: the tamperer's copy no longer matches everyone else's and is rejected.
- Metaphor flag, "one big shared spreadsheet in the cloud": misleading, because there is no central copy. Each node holds and checks its own copy. The node counts above support showing thousands of independent copies.
- The 80-byte header is tiny relative to a block of up to 4,000,000 weight units, which is why header-only light clients are practical. This is a sound basis for a "header vs body" visual.
- Bitcoin block height 969,864 implies the current block subsidy epoch is the one that began at block 840,000 (next halving at block 1,050,000), assuming the standard 210,000-block halving interval. The interval and subsidy amount were not verified against a source in this session.
- The United Kingdom hosting about 9.55% of discoverable Ethereum nodes (third after the US and Germany) is a UK-relevant figure, but it reflects where servers are hosted, including cloud data centres, not where owners live.

### Gaps
- "Reachable" Bitcoin nodes are only those accepting inbound connections. The number of non-listening full nodes is not measured by this tracker, and I found no reliable current estimate. Neither btcnodes.io page I read explained its methodology.
- ethernodes.org returned HTTP 403, so there is no second Ethereum node count to cross-check Etherscan. Different crawlers historically give different counts; confidence in "about 12,000" is medium.
- The number of Ethereum validators (as distinct from nodes) could not be retrieved: beaconcha.in returned HTTP 401. Only total ETH staked was obtained (see Key Question 2).
- Current Bitcoin block subsidy and halving schedule were not verified against a primary source in this session.
- I could not read the Etherscan gas limit chart values, so "60 million" rests on ethereum.org documentation rather than a direct on-chain reading for October 2026.

## Key Question 2: Consensus and finality (proof of work vs proof of stake, confirmation and finality times, real caveats to "immutable")

### Takeaway
Bitcoin's proof of work gives probabilistic settlement (about 10 minutes per block on average, with six confirmations the long-standing recommendation for high-value transfers), while Ethereum's proof of stake has 12-second slots and explicit finality after about 15 minutes. "Immutable" is an overstatement: reorganisations and 51% attacks have happened, mostly on smaller proof-of-work chains, and both Bitcoin and Ethereum have had accidental incidents.

### Cited Findings

#### (a) Well-established facts, safe to teach

- Proof of work, in the specification's own words: "To prove you did some extra work to create a block, you must create a hash of the block header which does not exceed a certain value." Difficulty is recalculated every 2,016 blocks against an ideal of 1,209,600 seconds (two weeks). — [Bitcoin developer guide](https://developer.bitcoin.org/devguide/block_chain.html)
- The whitepaper's six network steps: (1) new transactions are broadcast to all nodes; (2) each node collects new transactions into a block; (3) each node works on finding a difficult proof-of-work for its block; (4) when a node finds one, it broadcasts the block; (5) nodes accept the block only if all transactions in it are valid and not already spent; (6) nodes express acceptance by working on the next block, "using the hash of the accepted block as the previous hash." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- Ethereum switched from proof of work to proof of stake at The Merge on 15 September 2022 (06:42:42 UTC). "Proof-of-work has now been deprecated. Ethereum no longer uses proof-of-work as part of its consensus mechanism." — [ethereum.org: history](https://ethereum.org/en/history/) and [ethereum.org: proof-of-work](https://ethereum.org/en/developers/docs/consensus-mechanisms/pow/)
- Ethereum proof of stake: "Time in proof-of-stake Ethereum is divided into slots (12 seconds) and epochs (32 slots)." "One validator is randomly selected to be a block proposer in every slot." "To participate as a validator, a user must deposit 32 ETH into the deposit contract." — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
- Since Pectra (7 May 2025), EIP-7251 "raises the maximum possible effective balance to 2048 ETH, meaning that a single validator can now stake between 32 and 2048 ETH." — [ethereum.org: Pectra](https://ethereum.org/en/roadmap/pectra/)
- Finality mechanism: validators vote on pairs of checkpoints (the first block of each epoch). "If a pair of checkpoints attracts votes representing at least two-thirds of the total staked ETH, the checkpoints are upgraded. The more recent of the two (target) becomes 'justified'. The earlier of the two is already justified because it was the 'target' in the previous epoch. Now it is upgraded to 'finalized'." — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
- "To revert a finalized block, an attacker would commit to losing at least one-third of the total supply of staked ETH." — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
- Slashing: "provable misbehavior, such as signing two conflicting blocks, results in slashing: part of the validator's stake is destroyed and the validator is forcibly removed from the network." — [ethereum.org: staking](https://ethereum.org/en/staking/)
- "It takes about 15 minutes for an Ethereum block to finalize." Single slot finality "is in the research phase. It is not expected to ship for several years." — [ethereum.org: single slot finality](https://ethereum.org/en/roadmap/single-slot-finality/)
- Bitcoin settlement is gradual: "Transactions do not become irreversible immediately. Instead, they accumulate confirmations, each making them increasingly difficult to reverse." Six confirmations is the "Minimum recommendation for high-value bitcoin transfers." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)
- Proof-of-work finality is probabilistic in general: "The more blocks were mined on top of a specific block N, the higher confidence that the transactions in N were successful and would not be reverted." — [ethereum.org: proof-of-work](https://ethereum.org/en/developers/docs/consensus-mechanisms/pow/)
- What a majority attacker can and cannot do: "An attacker can only try to change one of his own transactions to take back money he recently spent"; the attack does not allow "creating value out of thin air or taking money that never belonged to the attacker." — [Bitcoin whitepaper, section 11](https://nakamotoinstitute.org/library/bitcoin/)
- Before the switch, Ethereum miners "were collectively consuming about 70 TWh/yr (about the same as the Czech Republic)." — [ethereum.org: proof-of-work](https://ethereum.org/en/developers/docs/consensus-mechanisms/pow/)

- A practical exchange policy: Kraken "only credits Bitcoin deposits...after four confirmations, which takes approximately 40 minutes" (page last updated 1 October 2026). — [Kraken support](https://support.kraken.com/articles/203325283-cryptocurrency-deposit-processing-times)

#### (c) Contested or commonly misstated: documented caveats to "immutable"

- Bitcoin, 15 August 2010 (value overflow incident): "block 74638 contained a transaction that created 184,467,440,737.09551616 bitcoins for three different addresses." A fixed client was published "within five hours" containing a soft-forking rule change, and "The 'good' block chain overtook it at a block height of 74691 at which point all nodes accepted the 'good' blockchain." — [Bitcoin Wiki: Value overflow incident](https://en.bitcoin.it/wiki/Value_overflow_incident)
- Bitcoin, March 2013: a block accepted by version 0.8 nodes was rejected by older nodes, splitting the chain. "BTCGuild and Slush downgraded their Bitcoin 0.8 nodes to 0.7 so their pools would also reject the larger block", abandoning the 0.8 chain. "During this time there was at least one large double spend", described as an experiment and not malicious. — [BIP-50 post-mortem](https://github.com/bitcoin/bips/blob/master/bip-0050.mediawiki)
- Ethereum Beacon Chain, 25 May 2022 (before The Merge): "at 08:55 UTC, a 7 block re-org occurred on the beacon chain." Causes were "purely accidental" (a late block plus uneven client rollout of a fork-choice update), and "The re-org did not result in loss of finality." — [Barnabé Monnot analysis](https://barnabe.substack.com/p/pos-ethereum-reorg)
- Ethereum, 11 and 12 May 2023: the Beacon Chain stopped finalising for 3 epochs (about 25 minutes) and then for 8 epochs (over an hour). Transactions continued to be processed; patches were released for the Prysm and Teku clients. (Search snippet only; the Offchain Labs post-mortem returned HTTP 403.) — [The Block, May 2023](https://www.theblock.co/post/230680/ethereum-beacon-chain-finality-issue) and [The Block: patches](https://www.theblock.co/post/230723)
- Ethereum Classic, 31 July to 1 August 2020: an attacker replaced blocks 10904147 to 10907761 and double-spent "807,260 ETC ($5.6 million)", having rented hash power from NiceHash for "approx 17.5 BTC (~$192,000)". — [Bitquery investigation](https://bitquery.io/blog/attacker-stole-807k-etc-in-ethereum-classic-51-attack)
- Smaller proof-of-work coins, 2019 to 2020: MIT's Digital Currency Initiative detected "over 40 reorgs" six or more blocks deep on Bitcoin Gold, Hanacoin, Vertcoin, Verge, Expanse and Litecoin Cash. "Some of these reorgs contained double-spends and were hundreds of blocks deep." Rental markets "reduced the fixed costs for an attacker to zero." — [MIT DCI: 51% attacks](http://www.dci.mit.edu/projects/51-percent-attacks)
- Monero, 14 to 15 September 2025: an 18-block reorganisation at height 3,499,659 erased "36 minutes of transaction history" and invalidated 118 transactions after the Qubic mining pool released a privately mined chain. The article does not confirm any double spend, and whether Qubic held a true majority "was questioned". — [Decrypt, 15 September 2025](https://decrypt.co/339424/moneros-largest-reorg-erases-36-minutes-transaction-history)
- Ethereum Classic January 2019 (about $1.1 million double-spent) and Bitcoin Gold May 2018 (about $18 million) are widely reported, but I only have a secondary summary for the amounts (search snippet only). The primary Coinbase report on ETC returned HTTP 403. — [ChainUp summary](https://chainup.com/blog/51-percent-attacks-explained/); primary not opened: [Coinbase blog](https://www.coinbase.com/blog/ethereum-classic-etc-is-currently-being-51-attacked)
- Source conflict to avoid: the ChainUp summary says the August 2020 Ethereum Classic attack reorganised "over 7,000 blocks" and double-spent $5.6 million. Bitquery's on-chain investigation ties the $5.6 million to the 31 July to 1 August attack covering roughly 3,600 blocks. Ethereum Classic suffered more than one attack that month, and the secondary source appears to merge them. Use the Bitquery figures. — [Bitquery](https://bitquery.io/blog/attacker-stole-807k-etc-in-ethereum-classic-51-attack); contradicted by [ChainUp](https://chainup.com/blog/51-percent-attacks-explained/)

#### Step-by-step for animators: Ethereum finality

1. Every 12 seconds (one slot) one randomly selected validator proposes a block. — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
2. Other validators vote (attest). 32 slots make an epoch; the first block of each epoch is a checkpoint. — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
3. When votes representing at least two-thirds of total staked ETH link two checkpoints, the newer one becomes "justified". — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
4. When the next checkpoint is justified on top of it, the earlier one is upgraded to "finalized". Documented time: about 15 minutes. — [ethereum.org: single slot finality](https://ethereum.org/en/roadmap/single-slot-finality/)
5. After that, reverting it would require an attacker to lose at least one-third of all staked ETH. — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)

### Inferences
- Arithmetic check on finality: one epoch is 32 × 12 seconds = 6.4 minutes, and finalisation needs two further checkpoint justifications, so the minimum is about 12.8 minutes; "about 15 minutes" is the documented round figure. Either is defensible if labelled "about".
- In the 2010 incident the bad chain was displaced after 74691 − 74638 = 53 blocks, which is the deepest reorganisation of Bitcoin I found documented.
- I found no documented successful 51% double-spend attack against Bitcoin itself or against Ethereum since The Merge. The safe teaching line is "has not happened on Bitcoin or Ethereum; has happened repeatedly on smaller proof-of-work chains", not "cannot happen".
- Metaphor flag, "miners solve complex maths puzzles": misleading. The specification describes repeated hashing of the header until the result does not exceed a target, which is brute-force guessing, closer to a lottery than to solving an equation.
- Metaphor flag, "padlock clicks shut": reasonable for Ethereum's justified-then-finalized step, but wrong for Bitcoin, where confidence builds with each confirmation and never becomes an absolute lock. A thickening wall or rising confidence meter is more accurate for Bitcoin.
- Metaphor flag, "51% attacker steals everyone's coins": wrong per whitepaper section 11. The attacker can reverse their own recent payments (double-spend) and censor, but cannot take coins that were never theirs or mint new ones.
- The 2023 finality delays show a useful distinction for beginners: Ethereum kept producing blocks and processing transactions while finality paused, and no finalised block was reverted. Confidence medium, because this rests on search snippets.

### Gaps
- No primary source was opened for the May 2023 Ethereum finality incident (HTTP 403 on the Offchain Labs post-mortem) or for the January 2019 Ethereum Classic and May 2018 Bitcoin Gold attacks.
- I did not find a current, sourced estimate of what a 51% attack on Bitcoin would cost in 2026; the "$6 billion" figure in one secondary source is unsupported and should not be used.
- How often one-block stale blocks occur on Bitcoin in 2026 was not researched.
- Exchange confirmation requirements for Ethereum and for layer 2 deposits were not readable on the Kraken page (the table did not load).

## Key Question 3: Wallets (keys and addresses, seed phrases, hierarchical wallets, custody, hardware wallets, smart-contract wallets and passkeys)

### Takeaway
A private key produces a public key, which is hashed to produce an address; the direction cannot be reversed. "A wallet holds keys, not coins" is accurate for ordinary self-custody wallets, but needs two qualifications: in a custodial account the provider holds the keys, and in a smart-contract wallet the assets sit in an on-chain contract whose code decides which keys or passkeys may act.

### Cited Findings

#### (a) Well-established facts, safe to teach

- Bitcoin: "secp256k1 private keys are 256 bits of random data"; the private key is "deterministically transformed into an secp256k1 public key"; the public key is hashed to a pubkey hash, which is encoded as an address for sharing. A signature "lets the pubkey script verify that Bob owns the private key which created the public key." — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Ethereum: the private key is "64 hex characters"; the public key is "generated from the private key using the Elliptic Curve Digital Signature Algorithm"; the address is obtained by "taking the last 20 bytes of the Keccak-256 hash of the public key and adding 0x to the beginning", giving a 42-character address. — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/)
- One-way relationship: "It is possible to derive new public keys from your private key, but you cannot derive a private key from public keys." — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/)
- "An account is not a wallet. A wallet is an interface or application that lets you interact with your Ethereum account." — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/)
- "Wallet providers don't have custody of your funds. They just provide you a window to see your assets on Ethereum and tools to easily manage them." — [ethereum.org: wallets](https://ethereum.org/en/wallets/)
- Bitcoin balance is a ledger fact, not a stored object: "When your Bitcoin wallet tells you that you have a 10,000 satoshi balance, it really means that you have 10,000 satoshis waiting in one or more UTXOs." — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Ethereum has two account types: "Externally-owned account (EOA) – controlled by anyone with the private keys" and "Contract account – a smart contract deployed to the network, controlled by code." Each account has a nonce, balance, codeHash and storageRoot. — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/)
- BIP-39 word counts: 128 bits of entropy plus a 4-bit checksum gives 12 words; 160+5 gives 15; 192+6 gives 18; 224+7 gives 21; 256+8 gives 24. The checksum is "the first ENT / 32 bits of its SHA256 hash." — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
- BIP-39 word list: 2,048 words, each "encoding a number from 0-2047" (11 bits per word); the list is built so that "it's enough to type the first four letters to unambiguously identify the word." — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
- BIP-39 seed derivation: PBKDF2 with HMAC-SHA512, 2,048 iterations, the mnemonic as password and "mnemonic" plus an optional passphrase as salt, producing a 512-bit seed. — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
- BIP-32 hierarchical deterministic wallets: a master key is computed as HMAC-SHA512 with key "Bitcoin seed" over the seed, and a tree of child keys is derived from it. An extended public key lets one "derive child public keys of a given parent key without knowing any private key." Warning in the spec: "Knowledge of a parent extended public key plus any non-hardened private key descending from it is equivalent to knowing the parent extended private key." — [BIP-32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki)
- BIP-44 path: `m / purpose' / coin_type' / account' / change / address_index`. Purpose is fixed at 44'; coin type gives "a separate subtree for every cryptocoin"; change uses "0 ... for external chain and constant 1 for internal chain (also known as change addresses)"; "Address gap limit is currently set to 20." — [BIP-44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki)
- Seed phrase as the only backup: "Wallets will often give you a seed phrase that you must write down somewhere safe. This is the only way you'll be able to recover your wallet." — [ethereum.org: wallets](https://ethereum.org/en/wallets/)
- Custodial accounts: "Centralized exchanges will link your wallet to a username and password that you can recover in a traditional way. Just remember you're trusting that exchange with custody over your funds." — [ethereum.org: wallets](https://ethereum.org/en/wallets/)
- Custody risk: "When a third party controls your keys, you rely entirely on their security and honesty, and history has shown that exchanges and online wallets can be hacked, fail, or freeze access to funds." — [bitcoin.org: Securing your wallet](https://bitcoin.org/en/secure-your-wallet)
- Hardware wallets are "little devices that are designed from the root to be a wallet and nothing else. No software can be installed on them, making them very secure against computer vulnerabilities and online thieves." Cold storage means "storing a wallet in a secured place that is not connected to the network." — [bitcoin.org: Securing your wallet](https://bitcoin.org/en/secure-your-wallet)
- Loss is permanent in self-custody: "If you permanently lose access to your wallet...your funds are gone permanently. No one...can recover funds that you permanently lose from a self-custodied wallet." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)

#### Smart-contract wallets, account abstraction and passkeys as deployed

- For an ordinary key-controlled account, "if you have the private key you can do anything within the rules of the Ethereum Virtual Machine (EVM); if you do not have the private key you can do nothing." Smart contract wallets let users "define your own flexible security rules", "recover your account if you lose the keys", "batch transactions together", and "pay someone else's gas, or have someone else pay yours." — [ethereum.org: account abstraction](https://ethereum.org/en/roadmap/account-abstraction/)
- ERC-4337: the EntryPoint contract "was deployed to Ethereum Mainnet on 1st March 2023 and has facilitated the creation of over 26 million smart wallets and 170 million UserOperations" (figure as shown on the page on 4 October 2026; the page does not date it). — [ethereum.org: account abstraction](https://ethereum.org/en/roadmap/account-abstraction/)
- EIP-7702 went live with Pectra on 7 May 2025 and lets users "set their address to be extended with a smart contract", enabling "transaction bundling, gasless transacting and custom asset access for alternative recovery schemes." — [ethereum.org: Pectra](https://ethereum.org/en/roadmap/pectra/)
- EIP-7702 mechanics (status: Final): a new transaction type lets an externally owned account set its code to a delegation indicator `0xef0100 || address`, which points to contract code that then runs in the account's context. The delegation stays until a later transaction changes it or clears it by delegating to the zero address. Stated motivations are batching, sponsorship and privilege de-escalation. — [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)
- EIP-7702 risk stated in the spec: "The code specified by an authorization has unrestricted access to the account and must always be closely audited by the wallet. Few users have the level of sophistication to reasonably verify the code they are delegating to." A poorly implemented delegate can "allow a malicious actor to take near complete control over a signer's EOA." — [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)
- Passkeys at protocol level: Fusaka (3 December 2025) added the secp256r1 precompile (EIP-7951). "For users, this unlocks device-native signing and passkeys. Wallets can tap into Apple Secure Enclave, Android Keystore, hardware security modules (HSMs), and FIDO2/WebAuthn directly." — [ethereum.org: Fusaka](https://ethereum.org/en/roadmap/fusaka/)
- Passkeys in a deployed smart-account product: Safe describes passkeys as "public and private key pairs", where "the private key is secured in the user's device"; "Passkeys eliminate the need for users to store seed phrases securely"; they "are stored in a device secure element" and "can also be synced across multiple devices"; a dedicated module verifies the passkey signature so it can act as a signer. — [Safe docs: passkeys](https://docs.safe.global/advanced/passkeys/overview)

#### (b) Fast-changing figures (need an "as of" date)

- Early EIP-7702 uptake: more than 11,000 authorisations on Ethereum within a week of Pectra in May 2025 (search snippet only). — [The Block](https://www.theblock.co/post/354414/smart-wallet-adoption-surges-after-pectra-upgrade)

#### (c) Contested or commonly misstated

- "A wallet holds keys, not coins." Accurate for self-custody: the coins are entries on the ledger (UTXOs on Bitcoin, account balances on Ethereum) and the wallet stores keys and builds signatures. — [ethereum.org: wallets](https://ethereum.org/en/wallets/) and [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Qualification 1, custodial: in an exchange account the user holds neither coins nor keys; the exchange has custody and the user relies on its "security and honesty". — [ethereum.org: wallets](https://ethereum.org/en/wallets/) and [bitcoin.org: Securing your wallet](https://bitcoin.org/en/secure-your-wallet)
- Qualification 2, smart-contract wallets: the account is a contract "controlled by code", so the assets belong to the contract's address and keys or passkeys are signers that the code authorises. — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/) and [Safe docs: passkeys](https://docs.safe.global/advanced/passkeys/overview)
- "An address is your public key." Accurate version: on both chains the address is derived from a hash of the public key. — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/) and [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- "Bitcoin addresses are base58." The developer guide describes the original base58 format only. Modern native SegWit addresses beginning "bc1" use the bech32 encoding defined in BIP-173; I did not open that specification in this session, so verify before teaching. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html); not opened: [BIP-173](https://github.com/bitcoin/bips/blob/master/bip-0173.mediawiki)
- "EIP-7702 makes your account a smart account temporarily." ethereum.org's transactions page says type 4 transactions "allow EOAs to temporarily behave like smart contract accounts", but the specification sets a delegation that remains until changed or cleared. Teach "until you change or remove it". — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/); contradicted by [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)
- "Passkey wallets have no keys." Accurate version: a passkey is a key pair held in the device's secure hardware and optionally synced; there is no seed phrase to write down, but there is still a private key. — [Safe docs: passkeys](https://docs.safe.global/advanced/passkeys/overview)
- "Lost keys mean lost funds, always." True for ordinary self-custody accounts. Smart-contract wallets can be built to "recover your account if you lose the keys", and custodial accounts can be recovered "in a traditional way", in exchange for trusting the custodian. Recovery exists only if it was set up beforehand. — [ethereum.org: account abstraction](https://ethereum.org/en/roadmap/account-abstraction/) and [ethereum.org: wallets](https://ethereum.org/en/wallets/)
- The ethereum.org account abstraction page still says EIP-7702 "is scheduled for May 7, 2025"; that wording is stale. It activated on that date. — [ethereum.org: Pectra](https://ethereum.org/en/roadmap/pectra/)

#### Step-by-step for animators: from seed phrase to address

1. The wallet generates random entropy (128 bits for 12 words, 256 bits for 24). — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
2. It appends a checksum taken from the SHA-256 hash of that entropy, splits the result into 11-bit groups, and maps each group to one of 2,048 words. — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
3. The words (plus optional passphrase) are stretched with PBKDF2-HMAC-SHA512, 2,048 rounds, into a 512-bit seed. — [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
4. The seed yields a master key, from which a tree of child private keys is derived. — [BIP-32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki)
5. The path `m/44'/coin'/account'/change/index` selects which branch is used for which coin, account and address. — [BIP-44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki)
6. Each private key produces a public key, which is hashed to produce an address. — [ethereum.org: accounts](https://ethereum.org/en/developers/docs/accounts/)

### Inferences
- Because the last word carries checksum bits, a 12-word phrase cannot be made by picking any 12 words from the list; most arbitrary combinations fail the checksum. This follows from the BIP-39 table and supports telling beginners that the wallet must generate the phrase.
- One seed phrase backs up every address in the wallet, across coins, because all keys sit on one tree (BIP-32 and BIP-44). An accurate visual is a single root branching into many keys, not one phrase per address.
- Metaphor flag, "leather wallet with coins inside": misleading. A keyring that unlocks entries on a public ledger is closer to the documented mechanism.
- Metaphor flag, "seed phrase is a password": misleading. It cannot be reset or changed for the same keys, and anyone who has it can derive every key. "Master key backup" is closer.
- Metaphor flag, "hardware wallet is a USB stick holding your crypto": misleading. The bitcoin.org description supports showing a device that keeps keys away from the internet-connected computer; the coins remain on the ledger.
- For an EIP-7702 account the original private key still exists alongside the delegated code. The EIP text I read warns about malicious delegates but the extract did not state the key-retention point explicitly, so treat "the seed phrase still controls the account after upgrading" as likely but unverified here.

### Gaps
- Current adoption figures for EIP-7702 and passkey wallets in 2026 are unreliable. A search summary claimed "over 27 million delegated accounts" by September 2026 without a traceable primary source; I could not verify it and it should not be used.
- Coinbase's smart wallet (Base Account) documentation had moved and could not be read, so there is no primary source here for how the largest consumer passkey wallet handles storage and recovery.
- Passkey caveats (binding to a web domain, dependence on Apple or Google account sync, what happens if the device and sync account are both lost) were not stated on the Safe page I read. Needs a dedicated source before any lesson on passkey recovery.
- Estimates of permanently lost bitcoin (commonly quoted as roughly 2.3 to 4 million BTC, attributed to Chainalysis and River) could not be verified: River's blog did not resolve and Ledger's page is blocked for UK visitors ("Due to new rules in the UK, certain Ledger.com webpages are restricted"). Do not use a figure without a primary source.
- That the same private key gives the same address on every EVM-compatible network was not sourced in this session.
- Taproot and Schnorr signatures (BIP-340/341) and bech32 addresses (BIP-173/350) were not opened.

## Key Question 4: Transactions (lifecycle, fees, typical costs and waits in 2026, irreversibility, user errors)

### Takeaway
A transaction is signed on the user's device, broadcast to nodes, held in their mempools, included in a block by a miner or validator, and then buried under further blocks; it cannot be reversed afterwards. On 4 October 2026 fees were very low on both chains (about 1 sat/vB or less on Bitcoin; an Ethereum base fee of 0.174 gwei, roughly one US cent for a simple transfer), but both are market prices that rise sharply under congestion.

### Cited Findings

#### (a) Well-established facts, safe to teach

- Bitcoin transactions spend previous outputs: "Each input spends the satoshis paid to a previous output." A UTXO can only be spent once and in full, so surplus is returned to the sender as a change output. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Bitcoin fee is implicit: "the full value of the included UTXOs must be spent or given to a miner as a transaction fee." Fees are "calculated based on current demand for space in mined blocks with fees rising as demand increases." — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Bitcoin fee rates are quoted per virtual byte, where virtual size is transaction weight divided by four. — [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki)
- Ethereum transaction fields: `from`, `to`, `signature` ("generated when the sender's private key signs the transaction"), `nonce` ("a sequentially incrementing counter"), `value`, `input data`, `gasLimit`, `maxPriorityFeePerGas`, `maxFeePerGas`. — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)
- Ethereum lifecycle as documented: (1) "A transaction hash is cryptographically generated"; (2) "The transaction is then broadcasted to the network and added to a transaction pool"; (3) "A validator must pick your transaction and include it in a block"; (4) "As time passes the block containing your transaction will be upgraded to 'justified' then 'finalized'." — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)
- "Once a block is 'finalized' it could only ever be changed by a network level attack that would cost many billions of dollars." — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)
- Gas: "the unit that measures the amount of computational effort required to execute specific operations on the Ethereum network." One gwei is "one-billionth of an ETH". "An ETH transfer requires 21,000 units of gas." Fee formula: "units of gas used * (base fee + priority fee)." — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- EIP-1559: "The base fee per gas is adjusted up and down by the protocol based on how congested the network is." The gas target is the block gas limit divided by an elasticity multiplier of 2; the base fee moves by at most one-eighth (12.5%) per block. — [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)
- "The base fee is always burned (i.e. it is destroyed by the protocol)." Only the priority fee goes to the block producer. — [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)
- "The transaction sender is refunded the difference between the max fee and the sum of the base fee and tip." — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- Fees exist to stop spam: "By requiring a fee for every computation executed on the network, we prevent bad actors from spamming the network." — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- Failed transactions still cost money: "if a transaction runs out of gas during execution...all the gas provided will still be consumed for the work performed." — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- Irreversibility: "A Bitcoin transaction cannot be reversed, it can only be refunded by the person receiving the funds." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)
- Ethereum transaction types in use: type 2 (EIP-1559), type 3 (blob transactions, EIP-4844, used by rollups), type 4 (EIP-7702). — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)

#### (b) Fast-changing figures (need an "as of" date)

- Bitcoin recommended fee rates on 4 October 2026: fastest 1 sat/vB, half-hour 0.517, one-hour 0.254, economy 0.2, minimum 0.1 sat/vB. — [mempool.space precise fee API](https://mempool.space/api/v1/fees/precise)
- The older mempool.space endpoint rounds to whole numbers and showed 1 sat/vB for every tier at the same time, so wallets and sites may display "1 sat/vB" when the market rate is lower. — [mempool.space recommended fee API](https://mempool.space/api/v1/fees/recommended)
- Bitcoin mempool on 4 October 2026 (one node's view): 69,012 unconfirmed transactions totalling 39,483,684 vbytes; the highest fee-rate band was about 1.99 sat/vB. — [mempool.space mempool API](https://mempool.space/api/mempool)
- Sub-1 sat/vB fees are relayed by default in current Bitcoin Core. The 30.0 release notes (released 10 October 2025) state: "The default minimum relay feerate (-minrelaytxfee) and incremental relay feerate (-incrementalrelayfee) have been changed to 0.1 satoshis per vB." I did not check whether an earlier point release made the same change first. — [Bitcoin Core 30.0 release notes](https://bitcoincore.org/en/releases/30.0/)
- An analysis of 1,105 data points from 9 June to 9 September 2026 reported the median Bitcoin fee rate "almost continuously" at 1 sat/vB, never above 7 sat/vB, and at or below 2 sat/vB in 90.4% of readings (search snippet only; secondary source). — [CryptoTicker](https://cryptoticker.io/en/bitcoin-network-fee-utxo-consolidation/)
- Ethereum on 4 October 2026, 16:24:55 UTC, block 26,120,169: base fee 0.174 gwei; low and average gas price 0.174 gwei, high 0.365 gwei; ETH price $2,698.37; a token swap estimated at $0.167 (standard) to $0.351 (rapid). — [Etherscan gas tracker](https://etherscan.io/gastracker)
- ethereum.org's live statistics on the same day showed "$0.071 Average transaction cost on the Ethereum blockchain" and "$0.0018 Average transaction cost on Ethereum backed networks" (layer 2). — [ethereum.org: layer 2](https://ethereum.org/en/layer-2/)
- Longer-run direction: average Ethereum gas prices fell from about 72 gwei in early 2024 to about 2.7 gwei by March 2025 (search snippet only; secondary source, low confidence). — [SQ Magazine](https://sqmagazine.co.uk/ethereum-gas-fees-statistics.md)
- Ethereum gas limit: validators raised it to 45 million in 2025 and then to 60 million in November 2025 without a hard fork, by signalling in the blocks they propose (search snippet only). — [The Block: 45 million](https://www.theblock.co/post/363763/ethereum-hits-45-million-block-gas-limit) and [Cointelegraph: 60 million](https://cointelegraph.com/news/ethereum-validators-push-gas-limit-60m-scaling)

#### (c) Contested or commonly misstated

- "Bitcoin's minimum fee is 1,000 satoshis." The developer guide still says "a minimum fee (currently 1,000 satoshis) has been required to broadcast a transaction", which is out of date. The current default relay floor is 0.1 sat/vB. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html); superseded by [Bitcoin Core 30.0 release notes](https://bitcoincore.org/en/releases/30.0/)
- "Ethereum fees go to miners." EIP-1559's text says "miners" because it predates The Merge; today blocks are proposed by validators, the base fee is burned, and only the tip is paid to the proposer. — [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559) and [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- "The fee depends on how much you send." On Bitcoin the fee depends on transaction size in vbytes and the going fee rate; on Ethereum on gas used and the gas price. Neither scales with the value transferred. — [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki) and [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- "A failed transaction costs nothing." False on Ethereum: gas is consumed for work performed. — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- "You can cancel or reverse a payment." No. A confirmed transaction "cannot be reversed, it can only be refunded by the person receiving the funds." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)

#### Common user errors

- Address poisoning, defined: scammers study "a target's transaction patterns, looking for frequently used addresses", then "algorithmically generate new crypto addresses until they create one that closely resembles the address that the target most often interacts with", then send "a small, seemingly harmless transaction from this newly generated address, effectively 'poisoning' the target's address book." The victim later copies the look-alike address from their history. — [Chainalysis, 23 October 2024](https://www.chainalysis.com/blog/address-poisoning-scam/)
- Scale of one campaign: 82,031 seeded look-alike addresses; "Only 0.03% of the fake addresses received more than $100 from victims"; total victim losses $69,720,993 across 2,774 addresses. In the May 2024 case nearly $68 million in wrapped bitcoin was sent to a poisoned address and most was later returned after negotiation. — [Chainalysis, 23 October 2024](https://www.chainalysis.com/blog/address-poisoning-scam/)
- December 2025 case: an investor lost about $50 million in USDT. They first sent a 50 USDT test to the correct address, then copied the address from a transaction history that had been poisoned with a 0.005 USDT transfer; "the first three and last four characters matched." — [ForkLog, 20 December 2025](https://forklog.com/en/news/investor-loses-nearly-50-million-in-address-spoofing-attack)
- Wrong network: exchanges state that if you send an asset using the wrong network, the deposit "won't be credited automatically and won't appear in your account"; recovery may be offered for a fee but is not guaranteed (search snippets only; Bitvavo returned HTTP 403 and CoinJar's page was geo-restricted). — [Bitvavo support](https://support.bitvavo.com/hc/en-us/articles/33523557113745-How-do-I-know-if-I-used-the-correct-network-for-my-crypto-deposit) and [Binance.US: unsupported asset recovery](https://support.binance.us/hc/en-us/articles/4404564207255-Unsupported-asset-recovery)

#### Step-by-step for animators: a Bitcoin payment

1. The wallet picks one or more UTXOs it controls as inputs. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
2. It creates outputs: one to the recipient's address and usually one change output back to the sender. Whatever is left over is the fee. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
3. It signs with the private key; the signature lets anyone verify the spender owns the key matching the public key. The private key is never broadcast. — [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
4. "New transactions are broadcast to all nodes." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
5. "Each node collects new transactions into a block" and miners work on a proof of work; the first to find one broadcasts the block. — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
6. Nodes accept the block only if every transaction is valid and unspent; that is the first confirmation. Each later block adds another, "each making them increasingly difficult to reverse." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/) and [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)

#### Step-by-step for animators: an Ethereum payment under EIP-1559

1. The wallet builds the transaction with a nonce, a gas limit, a max fee per gas and a max priority fee per gas, and signs it with the private key. — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)
2. It is broadcast and "added to a transaction pool". — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)
3. The validator chosen for a 12-second slot includes it in a block. — [ethereum.org: proof-of-stake](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)
4. The sender pays gas used × (base fee + tip). The base fee portion is burned; the tip goes to the proposer; any difference up to the max fee is refunded. — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
5. The protocol then adjusts the base fee for the next block, up if the block was above the gas target and down if below, by at most 12.5%. — [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)
6. The block is later justified, then finalized. — [ethereum.org: transactions](https://ethereum.org/en/developers/docs/transactions/)

### Inferences
- Cost of a simple ETH transfer at the 4 October 2026 reading: 21,000 gas × 0.174 gwei = 3,654 gwei = 0.000003654 ETH, which at $2,698.37 is about $0.0099, roughly one US cent before any tip. This is my calculation from the two cited figures and is far below ethereum.org's $0.071 "average transaction cost", which averages over more complex transactions. Quote either with its label, and do not present one cent as typical for all activity.
- How fast Ethereum fees can climb: a 12.5% rise per block compounds to roughly double in six consecutive full blocks (1.125^6 ≈ 2.03), about 72 seconds. This is arithmetic from EIP-1559 and is a sound basis for showing a fee meter rising during a rush.
- A Bitcoin mempool of about 39.5 million vbytes is many blocks' worth of waiting transactions, yet the top fee rate was under 2 sat/vB. The backlog is therefore mostly very low-fee transactions, and a payment at 1 sat/vB was still expected in the next block. "Low fee" and "empty mempool" are not the same thing.
- "The mempool" is not one global queue: mempool.space reports one node's view and ethereum.org describes "a transaction pool" held by nodes. An animation should show many nodes each holding pending transactions. I did not find a single sentence in a primary source stating this outright, so treat it as an inference from how the sources describe it.
- Metaphor flag, "coins fly from wallet A to wallet B": misleading. On Bitcoin old outputs are consumed and new ones created on the ledger; on Ethereum two balances are updated. Nothing travels between devices.
- Metaphor flag, "burned fee goes to the network or a treasury": wrong. The base fee is destroyed and paid to nobody.
- The December 2025 case shows that a test transaction does not protect a user who then copies the address from history. The accurate advice is to check the whole address against the original source every time, since matching first and last characters is exactly what the attack fakes.
- All fees above are in US dollars or native units; no sterling conversion was sourced. The site should convert at publication time and date the figure.

### Gaps
- No BTC/USD or GBP price was captured, so Bitcoin fees are given only in sat/vB. A typical transaction size in vbytes was not sourced either, so no "typical Bitcoin fee in pounds" can be stated from these notes.
- Replace-by-fee and how a stuck transaction can be sped up or replaced before confirmation were not covered by the sources read; "pending transactions cannot be changed" should not be taught without checking this.
- The wrong-network guidance rests on search snippets from exchange help pages; no primary page was readable. A UK-accessible exchange help page should be found before teaching specifics on recovery.
- I did not verify whether sending to the same address on a different EVM network is recoverable in self-custody.
- Fee spikes: no sourced 2026 peak figures for either chain were collected, only the current lows.
- A secondary claim of "over 1 million address poisoning attempts every single day" on Ethereum appeared in a search summary with no traceable primary source; not used.

## Key Question 5: Layer 2 (rollups, blobs, fee reduction, share of activity, trust assumptions and stages, bridge risks)

### Takeaway
A rollup executes transactions on its own chain and posts compressed data plus either a fraud-proof window (optimistic) or a validity proof (zero-knowledge) to Ethereum, mostly in blobs since March 2024, which cut typical layer 2 fees by around 95%. Layer 2s now carry the large majority of tracked activity, but most are still Stage 0 or unrated on L2BEAT, only four small projects are Stage 2, and bridges remain the most-exploited component, including a $292 million loss in April 2026.

### Cited Findings

#### (a) Well-established facts, safe to teach

- Rollups, defined by L2BEAT: "L2s that periodically post state commitments to Ethereum. These commitments are validated by either Validity Proofs or are accepted optimistically and can be challenged via Fraud Proof mechanism within a certain fraud proof window." — [L2BEAT: value secured](https://l2beat.com/scaling/tvs)
- "An optimistic rollup is an approach to scaling Ethereum that involves moving computation and state storage offchain." Operators "bundle multiple offchain transactions together in large batches before submitting to Ethereum", as calldata or blobs. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
- Optimistic rollups assume batches are valid unless challenged: "anyone can challenge the results of a rollup transaction by computing a fraud proof"; the challenge period lasts "roughly seven days", and users withdrawing to Ethereum "must wait until the challenge period...elapses". Liquidity providers can front the funds sooner for a fee. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
- Optimistic rollup security "relies on the existence of one honest node". — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
- Sequencer: it "processes transactions, produces rollup blocks, and submits rollup transactions to the L1 chain." "Rollup operators can censor users by going offline completely, or by refusing to either produce blocks that include certain transactions." Users can "submit their transactions on L1 instead of to the sequencer", which the sequencer must then include within a time limit. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
- ZK-rollups "bundle (or 'roll up') transactions into batches that are executed offchain" and submit a validity proof, "a cryptographic assurance that the state-change proposed by the rollup is really the result of executing the given batch of transactions", which a verifier contract on Ethereum checks. — [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- "There are no delays when moving funds from a ZK-rollup to Ethereum because exit transactions are executed once the ZK-rollup contract verifies the validity proof." — [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- ZK-rollups still publish data: "state data for every transaction processed offchain to Ethereum". Most use "a 'supernode' (the operator) to execute transactions, produce batches, and submit blocks to L1." ZK-SNARKs need "a trusted setup"; ZK-STARKs do not but "produce larger proof sizes, which are more expensive to verify on Ethereum." — [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- Blobs (EIP-4844, live since Dencun on 13 March 2024): a blob is 4,096 field elements of 32 bytes, 131,072 bytes in total. Blob transactions carry "a large amount of data that cannot be accessed by EVM execution, but whose commitment can be accessed." — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) and [ethereum.org: history](https://ethereum.org/en/history/)
- Blobs are temporary: nodes must serve them for 4,096 epochs, "around 18 days"; ethereum.org says they are "pruned from clients after approximately 18 days." — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) and [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
- Blob space has its own price: "blob gas as a new type of gas. It is independent of normal gas and follows its own targeting rule, similar to EIP-1559." The blob fee is "deducted from the sender balance before transaction execution and burned." — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844)
- Stated rationale: "Rollups are in the short and medium term, and possibly in the long term, the only trustless scaling solution for Ethereum." — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844)
- ethereum.org's caveat for users: layer 2 "safety depends on the underlying technology, smart contract security, and maturity of the network", and users should "perform due diligence, starting with small transactions". — [ethereum.org: layer 2](https://ethereum.org/en/layer-2/)
- L2BEAT stage definitions. Stage 0: state roots posted on L1, data availability on L1, software to reconstruct state, and a proof system with at least 5 external actors able to submit a fraud proof. Stage 1: the only way (other than bugs) to indefinitely block an L2 to L1 message is "by compromising ≥75% of the Security Council"; upgrades by others need "at least a 7 days exit window". Stage 2: "the fraud proof system permissionless", "users have at least 30 days to exit in case of unwanted upgrades", and "the Security Council restricted to act only due to errors detected on chain." — [L2BEAT: stages](https://l2beat.com/stages)
- Bridges: "Bridges facilitate communication between blockchains through the transfer of information and assets." Trusted bridges "depend upon a central entity or system" and users "give up control of their crypto assets"; trustless bridges "operate using smart contracts and algorithms". Listed risks: smart contract risk ("a bug in the code that can cause user funds to be lost"), technology risk, censorship risk, and custodial risk ("bridge operators can collude to steal the users' funds"). — [ethereum.org: bridges](https://ethereum.org/en/bridges/)
- A bridged asset is a representation: wrapped bitcoin is "an Ethereum version of Bitcoin and not the original asset on the Bitcoin blockchain." — [ethereum.org: bridges](https://ethereum.org/en/bridges/)

#### (b) Fast-changing figures (need an "as of" date)

#### Bridge and cross-chain hacks (factual examples)

#### (c) Contested or commonly misstated

- "Layer 2s inherit Ethereum's security." Only to the degree the stage allows. Stage 0 requires a proper proof system with at least 5 external actors able to submit a fraud proof, but sets no exit-window or Security Council limits; at Stage 1 a Security Council can still intervene (it takes compromising ≥75% of it to block or push invalid messages) and other upgrades need a 7-day exit window; only Stage 2 requires a permissionless proof system, a 30-day exit window and a council restricted to on-chain-detected errors. — [L2BEAT: stages](https://l2beat.com/stages)
- "Every layer 2 is a rollup." No. L2BEAT separates rollups (22) from validiums and optimiums (3) and "others" (75). ethereum.org: "If data is stored somewhere else, then the project is not a direct Ethereum extension and is rather independent." — [L2BEAT: value secured](https://l2beat.com/scaling/tvs) and [ethereum.org: layer 2](https://ethereum.org/en/layer-2/)
- "Rollup data lives on Ethereum forever." Blob data is pruned after about 18 days; only the commitment remains accessible on-chain. — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844)
- "Withdrawals from layer 2 are instant." Native withdrawals from optimistic rollups wait out a challenge period of roughly seven days; faster exits depend on a third-party liquidity provider. ZK-rollup exits complete once the proof is verified. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/) and [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- "Zero-knowledge rollups are private." Not by default: the proof attests that execution was correct, and transaction state data is still published to Ethereum. — [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- "Layer 2s are decentralised like Ethereum." Most run a single sequencer or operator that can censor or go offline, with forced inclusion via Ethereum as the fallback. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/) and [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)
- Secondary sources disagree on stages and should not be used: one says only Arbitrum One and DeGate were Stage 1 as of April 2026, another that Arbitrum One, OP Mainnet and Base reached Stage 1 in January 2026. L2BEAT itself, read on 4 October 2026, lists Arbitrum One, Base and OP Mainnet all at Stage 1. Use L2BEAT directly and date it. — [L2BEAT: scaling summary](https://l2beat.com/scaling/summary); contradicted by [Eco](https://eco.com/support/en/articles/14798699-best-ethereum-l2s-in-2026-fees-tvl-tps-compared) and [BlockEden](https://blockeden.xyz/blog/2026/02/01/stage-1-fraud-proofs-arbitrum-optimism-base-l2-security/)

#### Step-by-step for animators: a payment on an optimistic rollup

1. The user signs a transaction and sends it to the rollup's sequencer, which processes it and produces a rollup block. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
2. The operator bundles many transactions into a batch and posts the compressed data to Ethereum, usually in blobs. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
3. A commitment to the blob is recorded on Ethereum; the blob data itself is kept by nodes for about 18 days and then pruned. — [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844)
4. The rollup also posts a claim about its new state. During a window of roughly seven days anyone can dispute it with a fraud proof. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)
5. If nobody successfully disputes it, the state is accepted and withdrawals to Ethereum that depend on it can complete. — [ethereum.org: optimistic rollups](https://ethereum.org/en/developers/docs/scaling/optimistic-rollups/)

For a ZK-rollup, replace steps 4 and 5 with: the operator generates a validity proof, a verifier contract on Ethereum checks it, and the state is accepted as soon as the proof verifies. — [ethereum.org: ZK-rollups](https://ethereum.org/en/developers/docs/scaling/zk-rollups/)

- From the L2BEAT figures, layer 2s and related chains produced about 1,189 user operations per second against 18.54 on Ethereum, about 98% of the tracked total that day. One project (Lighter, at 624) accounts for over half of the layer 2 figure, and 425 came from projects L2BEAT classes as "others" rather than rollups. "Most activity is on layer 2" is safe; "98% of Ethereum usage is on rollups" is not, because the number is dominated by a few high-frequency chains and includes non-rollups.
- The day's figures imply a ratio of about 65x, while L2BEAT displays 70.09x; the displayed factor is probably calculated over a longer window. Quote L2BEAT's number as published.
- Activity and value are distributed very differently: Base and Arbitrum One hold most of the value ($16.25 billion and $11.52 billion), while the activity leaders are different projects. Any "biggest layer 2" claim must say which measure.
- The KelpDAO case is a strong teaching example because nothing on the blockchain itself was broken and no contract had a bug; the failure was a single off-chain verifier. It supports the line "the chain was not hacked, the bridge's trust assumption was".
- Metaphor flag, "express lane on the same motorway": misleading. A rollup is a separate chain with its own operator that reports back to Ethereum; show a separate track that periodically files a compressed record and proof with the main chain.
- Metaphor flag, "coins walk across a bridge": misleading. The documented mechanism is that assets are held on one chain while a representation is issued on the other. The KelpDAO forged message, which released tokens with nothing locked behind them, shows why this distinction matters.
- Metaphor flag, "ZK means hidden": avoid masks or blackout visuals. A proof being checked and stamped is more accurate.
- The roughly 95% Dencun fee drop is a measurement from the first day or two after the upgrade. Present it as "fell by around 95% when blobs were introduced in March 2024", with the growthepie attribution, and use the ethereum.org live figure for the current level.

## Key Question 6: Misconceptions (common beginner beliefs and the precise correction)

### Takeaway
Each of the standard beginner beliefs has a short, sourced correction, and in several cases the popular "correction" is itself too absolute (for example "lost keys can never be recovered" or "blockchains are immutable"). The accurate versions below are worded so they stay true for custodial accounts, smart-contract wallets and smaller chains.

### Cited Findings

- Belief: "Coins are stored in the wallet." Correction: coins are records on the blockchain; the wallet holds keys and shows the ledger. "Wallet providers don't have custody of your funds. They just provide you a window to see your assets on Ethereum." On Bitcoin a balance "really means that you have 10,000 satoshis waiting in one or more UTXOs." — [ethereum.org: wallets](https://ethereum.org/en/wallets/) and [Bitcoin developer guide: transactions](https://developer.bitcoin.org/devguide/transactions.html)
- Belief: "Blockchain is anonymous." Correction: it is pseudonymous and public. "Bitcoin is often perceived as an anonymous payment network. But in reality, Bitcoin is probably the most transparent payment network in the world." "All Bitcoin transactions are public, traceable, and permanently stored in the Bitcoin network." — [bitcoin.org: Protect your privacy](https://bitcoin.org/en/protect-your-privacy)
- Supporting detail: addresses carry no name, but "once addresses are used, they become tainted by the history of all transactions they are involved with"; "anyone can see the balance and transactions of any Bitcoin address." — [bitcoin.org: Protect your privacy](https://bitcoin.org/en/protect-your-privacy) and [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)
- Supporting detail: the whitepaper's privacy model is that "The public can see that someone is sending an amount to someone else, but without information linking the transaction to anyone", and it advises that "A new key pair should be used for each transaction." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- Supporting detail: law enforcement follows funds on public ledgers. After the Bybit theft the FBI published that the thieves had "converted some of the stolen assets to Bitcoin and other virtual assets dispersed across thousands of addresses on multiple blockchains." — [FBI public service announcement, 26 February 2025](https://www.ic3.gov/PSA/2025/PSA250226)
- Belief: "Transactions are instant and free." Correction: they are neither. Bitcoin blocks arrive "approximately every 10 minutes on average" and six confirmations is the recommendation for high-value transfers; Ethereum includes transactions in 12-second slots and takes "about 15 minutes" to finalise; every transaction pays a fee. — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know), [ethereum.org: single slot finality](https://ethereum.org/en/roadmap/single-slot-finality/) and [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- Supporting detail: fees were low but not zero on 4 October 2026: about 1 sat/vB or less on Bitcoin, an average of $0.071 on Ethereum and $0.0018 on layer 2 networks. — [mempool.space precise fee API](https://mempool.space/api/v1/fees/precise) and [ethereum.org: layer 2](https://ethereum.org/en/layer-2/)
- Belief: "A blockchain cannot be hacked." Correction, part 1: the ledgers of smaller proof-of-work chains have been rewritten by attackers. MIT recorded "over 40 reorgs" six or more blocks deep in 2019 to 2020, and Ethereum Classic lost 807,260 ETC to a double-spend in 2020. — [MIT DCI: 51% attacks](http://www.dci.mit.edu/projects/51-percent-attacks) and [Bitquery](https://bitquery.io/blog/attacker-stole-807k-etc-in-ethereum-classic-51-attack)
- Correction, part 2: Bitcoin itself has had software faults that required rewriting recent history, in August 2010 and March 2013. — [Bitcoin Wiki: Value overflow incident](https://en.bitcoin.it/wiki/Value_overflow_incident) and [BIP-50](https://github.com/bitcoin/bips/blob/master/bip-0050.mediawiki)
- Correction, part 3: most large losses happen around the chain, not in it. North Korea "was responsible for the theft of approximately $1.5 billion USD in virtual assets from cryptocurrency exchange, Bybit, on or about February 21, 2025"; $292 million was taken through the KelpDAO bridge in April 2026 although "No smart contract was broken". — [FBI public service announcement](https://www.ic3.gov/PSA/2025/PSA250226) and [OpenZeppelin](https://openzeppelin.com/news/lessons-from-kelpdao-hack)
- Belief: "Lost keys can be recovered." Correction: in self-custody they cannot. "No one...can recover funds that you permanently lose from a self-custodied wallet", and the seed phrase "is the only way you'll be able to recover your wallet." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know) and [ethereum.org: wallets](https://ethereum.org/en/wallets/)
- Qualification: recovery is possible where a third party or a contract was given that role in advance. Exchange accounts can be recovered "in a traditional way" at the cost of "trusting that exchange with custody", and smart-contract wallets can let users "recover your account if you lose the keys." — [ethereum.org: wallets](https://ethereum.org/en/wallets/) and [ethereum.org: account abstraction](https://ethereum.org/en/roadmap/account-abstraction/)
- Belief: "A payment can be reversed if I make a mistake." Correction: "A Bitcoin transaction cannot be reversed, it can only be refunded by the person receiving the funds." — [bitcoin.org: You need to know](https://bitcoin.org/en/you-need-to-know)
- Belief: "Whoever controls most of the mining can take my coins." Correction: a majority attacker "can only try to change one of his own transactions to take back money he recently spent" and cannot take "money that never belonged to the attacker." — [Bitcoin whitepaper](https://nakamotoinstitute.org/library/bitcoin/)
- Belief: "Ethereum is mined like Bitcoin." Correction: Ethereum has used proof of stake since 15 September 2022; "Ethereum no longer uses proof-of-work." — [ethereum.org: history](https://ethereum.org/en/history/) and [ethereum.org: proof-of-work](https://ethereum.org/en/developers/docs/consensus-mechanisms/pow/)
- Belief: "A layer 2 is as safe as Ethereum." Correction: safety "depends on the underlying technology, smart contract security, and maturity of the network"; L2BEAT rated only four projects Stage 2 on 4 October 2026. — [ethereum.org: layer 2](https://ethereum.org/en/layer-2/) and [L2BEAT: scaling summary](https://l2beat.com/scaling/summary)
- Belief: "If the address in my history looks right, it is right." Correction: scammers plant look-alike addresses in transaction histories; in a December 2025 loss of about $50 million "the first three and last four characters matched." — [Chainalysis](https://www.chainalysis.com/blog/address-poisoning-scam/) and [ForkLog](https://forklog.com/en/news/investor-loses-nearly-50-million-in-address-spoofing-attack)
- Belief: "A failed transaction is free." Correction: on Ethereum "all the gas provided will still be consumed for the work performed." — [ethereum.org: gas](https://ethereum.org/en/developers/docs/gas/)
- Belief: "A blockchain is run by one company or one computer." Correction: about 25,200 reachable Bitcoin nodes and about 12,100 discoverable Ethereum nodes each kept their own copy on 4 October 2026. — [BTC Nodes](https://btcnodes.io/) and [Etherscan node tracker](https://etherscan.io/nodetracker)
- Belief: "My exchange app is my wallet." Correction: with an exchange "you're trusting that exchange with custody over your funds"; "When a third party controls your keys, you rely entirely on their security and honesty." — [ethereum.org: wallets](https://ethereum.org/en/wallets/) and [bitcoin.org: Securing your wallet](https://bitcoin.org/en/secure-your-wallet)

### Inferences
- "Pseudonymous" is the precise word for both chains: addresses are not names, but every transaction is public and permanent, and linking one address to a person exposes its whole history. Lessons should avoid both "anonymous" and "everyone can see who you are".
- The strongest accurate form of the "cannot be hacked" correction has three layers, each with a dated example above: the ledger itself (smaller chains reorganised), the software (Bitcoin 2010 and 2013), and everything built around it (exchanges, bridges, user deception). For Bitcoin and post-Merge Ethereum the first layer has no documented successful attack that I could find.
- "Not your keys, not your coins" is directionally supported by the bitcoin.org and ethereum.org custody statements, but as a slogan it skips smart-contract wallets and regulated custody. The sourced wording is "whoever controls the keys controls the funds".
- "Transactions are irreversible" should be taught as "once confirmed". Before confirmation a transaction is only pending, and whether it can be replaced was not covered by my sources.
- Several misconceptions have a UK-specific consumer protection angle (no chargeback, no recovery service). That was outside this brief and nothing here should be read as a statement about UK regulation or compensation schemes.
